事情是这样的。

今天我重新打开了智慧药房的项目，原本只是想把国赛后的改进方案再整理一下。

结果一整天下来，我没有改小车的一行代码，反而把初赛、复赛、国赛的整个过程，从头到尾又讲了一遍。

讲到一半，我突然发现，过去几个月里那些看起来毫不相干的事情，其实都指向同一个问题。

RViz 卡顿、主从机网络、两次改坏 `sshd`、Docker 环境、双车串话题、识别结果迟到、代码被不同版本覆盖、比赛前 9 个终端的启动顺序，还有每天结束时留下的工作记录。

它们表面上有的是网络问题，有的是代码问题，有的是协作问题。

但说到底，都是工程工作流的问题。

<!-- more -->

## 没有故障，不等于系统没有问题

这次国赛最后，车 1 完成了一圈，车 2 没有跑完第二圈，现场没有出现明确故障，最后拿到了国赛三等奖。

这个结果当然不差。

双车隔离、导航、视觉、语音、交接和裁判通信的主链路都建立起来了。对一个从初赛一路临时补知识、补环境、补代码的项目来说，能走到这里，我已经挺满足了。

但今天重新看代码和记录时，我还是被一个问题卡住了。

没有故障，等于系统没有问题吗？

好像并不等于。

我们现在没有国赛当天完整的评分明细、终端日志、裁判端记录和全程录像。所以我不能看见源码里有一条风险路径，就拍脑袋说当天一定是在这里扣了分。

这是今天复盘时定下的第一条边界。

> 能从代码确认的，就写代码风险。能从测试记录确认的，就写测试结果。没有证据的当天结论，就老老实实标成未知。

不然复盘很容易变成赛后诸葛亮，讲得头头是道，证据一个没有。

## 1. 跑完一圈，不等于任务正确

赛前最后一次真实视觉联调里，有一个细节我现在回头看，还是觉得挺典型。

车 2 到达识别板 1 后，没有拿到有效识别结果。但它固定等了几秒，随后继续使用默认变量，把后面的路线跑完了。

从场外看，小车在动，导航点也一个个到达，甚至最后还能回到起点。

可这一圈的任务语义已经不可信了。

这就是我今天一直在想的「静默失败」。

程序没有崩溃，没有红色报错，机器人也没有原地罢工。它只是悄悄使用了错误前提，然后非常勤奋地把后面的事情全做完。

说真的，这种故障比直接报错更吓人。

直接报错至少会逼着人停下来。静默失败却会给你一种一切正常的错觉。

所以改进方案里排在最前面的，不是换一个更大的视觉模型，也不是继续给 OCR 加重试，而是把识别变成一笔真正的事务。

每一次识别都要带本圈编号、请求编号、图像时间和结果置信度。只接受本次停车以后采集的新画面，只接受属于当前请求的结果。结果通过范围和逻辑校验以后，再冻结成这一圈不可变的任务对象。

迟到的结果、上一圈的结果、长度不对的数组、互相冲突的多帧结果，都只能留下记录，不能偷偷改变正在执行的任务。

> 没收到，就是没收到。
> 不知道，就是不知道。
> 不能猜。

同样的问题还出现在状态机里。当前程序有些路径只要任意一个目标窗口成功，就会进入下一阶段。可比赛任务要求去两个窗口时，完成一个显然不叫完成。

后面我准备把每个必去窗口都拆成独立状态，只有全部目标都确认完成，状态机才允许继续。识别超时、部分完成、导航失败和返回失败也要有不同结果，不能最后全压成一个 `True` 或 `False`。

以前我觉得状态机就是让程序按顺序往下走。

现在我觉得，成熟的状态机更重要的能力，是知道什么时候绝对不能往下走。

## 2. 最高速度更高，整圈不一定更快

比赛准备时，我们真的花了不少时间调 TEB。

有一轮把最高速度从 `0.70 m/s` 提到 `0.75 m/s`，8 段纯导航时间只快了大约 1.82 秒。更离谱的是，C、A、B 几个关键弯道路段反而更慢了。

另一次只提高加速度，某个原本约 10 秒的路段跑到了 14 秒多。

参数表看起来更猛了，车却没有稳定地更快。

这一下把我之前很朴素的想法打碎了。机器人比赛里的性能，不是 YAML 文件里最大的那个数字，而是整条任务链的成功率、中位时间、P95 时间，还有最慢的那一圈。

如果一辆车直线快了半秒，却在进站时多调整两次，或者因为画面角度不稳定重新识别一轮，那点速度收益瞬间就没了。

回到今天的改进方案，我把性能优化放到了正确性和可观测性后面。

先去掉没有必要的固定等待，把识别改成结果到达就唤醒。先记录每一个导航段、清图、识别、播报、撤离和交接到底花了多久。先把一次完整任务拆成可以测量的阶段。

然后再谈快。

而且每次只改一个主要变量。候选参数先跑同样的任务，再同时比较中位数、P95、最慢圈、重试次数和成功率。没有明确收益，就恢复原来的基线。

这套办法听着不性感。

没有神奇参数，也没有一键提速 30%。

但它至少不会拿一次运气不错的最快圈，骗自己系统已经进步了。

## 3. 改进不是推倒重来，而是先把错误语义封住

今天上午写第一版改进方案时，我还在沿着现有代码一点点找风险。到了下午，我又让 Codex 带着现有代码，对照 [OpenNav Docking](https://github.com/open-navigation/opennav_docking)、ROS1 `actionlib`、Move Base Flex、ROS diagnostics 和 rosbag 这些成熟项目重新看了一遍。

我不是想把它们全塞进来。

恰恰相反，比较之后我删掉了几个看起来很高级、现在却不该做的方向。

项目没有必要为了一个精确停靠能力整体迁移 ROS2，也没必要因为主程序长，就立刻换成行为树。短距离确定性倒车也不该一股脑交给 TEB，因为优化器的方向偏好不是硬保证。

更合适的做法，是借结构，不照搬技术栈。

识别这类持续几秒、必须知道属于哪次请求的任务，用 ROS1 Action 表达目标、反馈、结果、超时和取消。普通导航先把车送到预停靠点，最后几十厘米再用站点专用的低速控制完成进站和静止确认。短距离撤离保留专用动作，但要加入后向障碍门控、里程计新鲜度、抢占和速度仲裁。

裁判通信也不能再用「TCP 连上了」作为验收。下一版会先做一个本地模拟裁判，把字段、频率、断线和重连一项项测完，再去官方界面核对真实结果。

原来需要严格操作 9 个终端的启动流程，也准备收敛成统一入口。系统先自动检查 ROS Master、两台车的定位、激光、里程计、相机、识别服务和外部连接，全部通过以后，仍然要由人显式发车。

自动启动，不等于自动乱跑。

整套改进会分阶段上车：

- **P0**：先封住错误推进。
- **P1**：再解决停靠、感知和运维波动。
- **P2**：只有前两层通过量化验收以后，才评估更复杂的视觉闭环、导航框架或速度优化。

这也是今天另一个很大的变化。

以前我会问哪个方案更先进。现在我更愿意问，当前最早没有通过的门槛是什么。

## 4. 两个半夜拆车的故事，最后变成了环境门禁

初赛刚开始时，我先读官方操作文档，再把需要使用的命令整理成 Markdown。后来考虑到电脑环境不兼容，又让 AI 帮我做了固定 Docker 容器。

测试 RViz 时画面很卡，我们才进一步做主从机和网络调整。

然后比较骚的事情来了。

改网络的过程中，我前后两次把 `sshd` 改坏。都是半夜把车拆开，用读卡器读取存储卡，再去修配置。

一次还能叫意外。

两次以后，就不能只怪手气不好了……

所以今天把工作流抽出来时，我对网络和 SSH 单独设了一道恢复门禁。

修改前要记录当前地址、路由、监听端口和服务状态，要给配置做带时间的备份，还要先确认物理恢复通道。改完不能只看旧 SSH 会话还活着，必须重新打开一个全新的登录。需要重启的配置，就要真的重启一次，确认 `sshd` 能自动起来。

旧连接没断，只能证明旧连接没断。

它证明不了下一次开机还能进得去。

容器也是一样。镜像能在当前机器运行，不等于环境已经被保存。真正需要留下的是 Dockerfile 或构建方法、镜像摘要、挂载关系、启动命令和恢复产物。

AI 的记忆也不能算备份。

它最多是一个索引，真正的项目记忆必须落在 Git、操作手册、工作记录、测试产物和发布清单里。

## 5. 多人可以一起查问题，但最终代码只能从一个出口出来

初赛时，我主要负责测试，另一个同学负责改代码。到了国赛，故障处理经常是两个人一起读代码、提建议，但最后代码仍然要由固定的维护者统一落下去。

这个规则看起来有点保守，但多人同时改机器人项目，真的很容易出现一种很抽象的情况。

每个人手里都有一个自称最新的版本。

然后真正上车时，谁也说不清容器里、电脑上、车 1 和车 2 分别是哪一份。

所以新的工作流保留了一个权威代码出口。大家都可以读、可以诊断、可以提补丁，Codex 和 Claude Code 也可以参与架构分析与方案设计，但被接受的实现要经过同一个维护者合并。

Git 也不需要每试一个参数就提交一次。

我最后采用的是双锚点。准备做一轮有意义的修改前，先保存当前已经接受的基线。中间实验可以不提交，或者只保留少量值得比较的候选。方案跑完验证并正式接受以后，再提交最终版本。

这比满屏的「再试一次」「最终版 2」「真的最终版」有用多了。

还有一个很容易被忽视的人，是最后负责测试和启动的同学。

容器、挂载、目录关系、实际启动顺序和最终产物，往往他最清楚。所以发布与归档不能只让写代码的人拍板，测试和运维负责人也必须确认，仓库里的版本和最后实际跑的版本确实一致。

## 6. 长项目不能每次打开对话都从第一步重来

今天把这些规则整理到最后，我碰到一个新问题。

如果把完整流程写成一条从头到尾的超长指令，每次调用都重新阅读规则、重建环境、分析架构、再走一遍测试，那这个 Skill 很快就会变成新的负担。

机器人项目不是做一次就结束的问答。

它可能今天在修视觉，明天退回网络，后天又因为新规则重新检查操作手册。一次对话结束，不代表项目回到了起点。

所以我最后把它做成了阶段感知的工作流。

项目发现、规则与手册、环境与连接、基线与架构、本地实现、实车验证、集成回归、发布与比赛、归档与复盘，一共 9 个阶段。

每次开始时，Agent 先判断现在在哪一段。人的当前描述优先，再读取项目里的状态文件，然后检查 Git、日志、测试证据和发布清单。AI 记忆只能提供线索，不能盖过仓库里的事实。

如果新证据证明前面的门禁其实没有通过，就退回去。

发现网络漂移，退回环境阶段。实车行为和架构图对不上，退回基线与架构阶段。冻结版本又做了阻塞性修复，就重新走受影响的验证，再生成新的提交、标签和发布清单。

这块我是真的觉得挺重要。

工作流不是一条只能向前的流水线，它更像游戏存档加关卡门禁。你不用每次新开对话都从新手村出发，但也不能靠一句「我记得这里做过」直接穿过还没验证的门。

Codex 可以用它，Claude Code 也可以用它。

我还专门在 Claude Code 里做了一次真实调用测试。它能发现项目级 Skill，通过 `/roscar-work-loop` 直接启动，然后先判断当前阶段，再给出下一道退出门槛。

当然，这套工作流远远谈不上成熟。

它不会自动把一台有风险的车变安全，也不能替代现场的人按下急停。AI 可以做架构分析、实验设计、参数整理和每天的工程记录，但运动授权、设计审核、最终验收和刹车权，还是必须在人手里。

> 方向盘可以逐步交出去。
> 刹车不能。

## 从一次比赛，沉淀下一次可复用的秩序

今天回头看，智慧药房这场比赛真正留下来的东西，可能不只是一个国三，也不只是两套能跑的 ROS 代码。

更重要的是，我开始知道怎么把一次混乱、漫长、充满临时判断的工程经历，重新整理成下一次还能复用的秩序。

先确认规则，再固定环境。先保存基线，再改代码。先证明正确，再追求速度。每次测试讲清楚证据边界，每天结束留下能让另一个人继续工作的记录。

这些事情都很笨。

但机器人真的跑起来以后，最可靠的往往就是这些笨办法。

我把这套流程整理成了一个开源 Agent Skill，支持 Codex 与 Claude Code。它现在还只是第一版，如果你也在做 ROS 实车、多机器人联调或者比赛项目，欢迎拿去试，也欢迎把踩过的坑继续补进去。
